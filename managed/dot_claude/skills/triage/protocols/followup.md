# Protocol: followup

Park a spinoff discovery that's out of scope for the current investigation, so it can be spun out as its own `/triage init` or a GitHub issue later without re-discovery.

## When to use

Mid-investigation you notice a *different* problem — an adjacent reliability signal, a deployment quirk, a missing doc — that isn't the bug you're triaging but mustn't be forgotten. Park it here and keep your focus on the current theory work.

A follow-up is **not** a theory. A theory is a candidate explanation of *this* bug and lives in `theories/`. A follow-up is a separate problem that earns its own future investigation. If you're unsure, ask: "does this explain the symptom I'm triaging?" If yes, it's a theory; if no, it's a follow-up.

## Args

`followup [free text describing the discovery]`

- With text: create one follow-up from the text.
- Without text: ask the user what they want to park (don't auto-scan — follow-ups come from human judgement about what's worth keeping). Offer a one-line summary of anything obvious you've seen this session, but let Stu confirm.

## Steps

### 1. Resolve and read

Find the investigation root. Read `followups.md` if it exists — to find the highest existing `F<id>` so the next one doesn't collide.

### 2. Assign the next follow-up ID

`F1`, `F2`, … — highest existing + 1. Never reuse, never renumber. (Single digit is fine; these are few. No zero-padding.)

### 3. Write the entry

If `followups.md` doesn't exist, create it with this header:

```markdown
# Follow-ups

_Spinoff candidates surfaced while triaging `<slug>`. Each entry should become
its own `/triage init` or a GitHub issue when this investigation closes. Not in
scope for the current session — focus stays on the bug being triaged._

---
```

Append the new entry. Keep it a short stub — enough to spin out without re-reading the whole investigation, no more:

```markdown
## F<id> — <short title>

**What was observed**
<one short paragraph — the discovery, with concrete pointers (dates, files,
log refs) so it can be re-found.>

**Why it matters**
<one or two bullets — the reliability/correctness/clarity signal, and any link
back to the current bug if there is one.>

**Next steps when spinning out**
<bullets — the first concrete actions, data to pull, who/what to check.>

**Owner**: TBD — assign when opening as its own investigation / issue.

---
```

### 4. Update README

Add the follow-up to the projected zone's `## Follow-ups` section: one bullet, `F<id>` + one-line summary. This mirrors how `hypothesise` live-writes `## Theories`; the section is also regenerated by `rollup` from `followups.md`, so a live edit and a later rollup stay consistent.

### 5. Log

Append `log/YYYY-MM-DDTHH-MM-followup-parked-F<id>.md` (one event per follow-up; if several are parked in one go, a single `followups-parked.md` covering all is fine):

```
# Follow-up parked: F<id>

Title: <short title>
Summary: <one line>
File: followups.md
```

### 6. Commit

Commit-before-edit applies. After: `triage: followup F<id>`.

### 7. Report

One line: the `F<id>`, its title, and a reminder that it'll surface in `## Follow-ups` on the next rollup and should be spun out (or explicitly dropped) when the investigation closes.

## Notes

- Follow-ups are deliberately terse stubs. The detail can be re-derived from `scope.md`, the log, and the entry's pointers — don't duplicate a whole analysis here.
- When an investigation closes, the closing log entry should call out, per follow-up, whether it's been spun out (and to where) or is still pending. This skill has no `close` subcommand yet — do this by hand in a final log event.
